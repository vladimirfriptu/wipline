# wipline

[English](README.md) · **Українська**

Показує, на якій фазі процесу стоїть кожна задача, у панелі терміналу, яку ви
тримаєте відкритою, і дозволяє вашій автоматизації заповнювати її саму.

## Навіщо це

Процес розробки легко тримати в голові, поки задача одна. Коли їх три-чотири
одночасно — перестає: ви повертаєтесь до гілки через два дні й не пам'ятаєте, чи
проганяли перевірки, чи чекають коментарі з рев'ю, чи ви свідомо пропустили тести.

Звичайна відповідь — дошка в тікетній системі, але в тікета чотири-п'ять статусів, а
у вашого реального процесу десяток кроків, більшості з яких дошка не бачить. Тому
знання живе в голові — і витікає.

wipline пише ці кроки в журнал, який тільки дописується, по одному файлу на задачу, і
дає три способи його побачити: таблицю, інтерактивну панель і однорядкове зведення.
Суть не в панелі. **Суть у тому, що більшість кроків відмічають себе самі** — див.
[Підключення автоматизації](#підключення-автоматизації), і саме через це варто
встановлювати.

## Встановлення

```bash
git clone https://github.com/vladimirfriptu/wipline ~/wipline
cd ~/wipline && ./install.sh
```

Лінкує `wipline`, `wipline-tui` і `wipline-pane` у `~/.local/bin`. Потрібні лише
Node 20+ і git. Нічого не пишеться поза `~/.local/bin` і вашим каталогом стану.

## Модель

**Короткий процес чи довгий — вирішуєте ви.** Список фаз живе в конфігу, а типовий —
це приклад, а не рекомендація.

Фаза несе один із шести станів:

| стан | що означає |
|---|---|
| *(немає)* | не записана в цьому колі |
| `wip` | у роботі саме зараз |
| `done` | завершена |
| `skip` | у цьому колі не потрібна |
| `open` | відпрацювала, але щось лишилось (знахідки рев'ю, червоні тести) |
| — | `clear` і `reset` — це події, які *знімають запис*, а не стани |

`done` і `skip` обидва вважаються пройденими. `wip` та `open` — ні, тому фаза
залишається вашим `next`.

Два способи зняти запис, і різниця між ними суттєва:

- **`clear`** знімає запис з однієї фази й нічого більше. Це щоденне виправлення
  помилкової відмітки, і саме це робить `space` у панелі на вже проставленій фазі.
- **`reset`** знімає запис із цієї фази **й з усіх наступних**, і рахує нове коло —
  для випадку, коли робота справді відкотилася: новий код потребує нових перевірок,
  нового рев'ю, нового тестування. У панелі клавіші для нього свідомо немає;
  використовуйте `wipline reset <phase>`.

Нічого ніколи не видаляється. `wipline history` показує кожне коло, тому задача, що
пройшла процес тричі, досі розкаже, що сталося першого разу.

## Використання

```bash
wipline done checks              # задачу бере з імені поточної гілки
wipline wip dev                  # відмітити, над чим працюєте
wipline skip qa --detail "reason=docs-only"
wipline clear checks             # зняти відмітку тільки з цієї фази
wipline reset dev                # назад у dev, усе після нього відкривається
wipline get                      # KEY=value, для скриптів
wipline board                    # усі задачі в роботі
wipline history ACME-42          # увесь журнал, по колах
wipline-tui                      # інтерактивна панель
wipline-pane toggle              # ...усередині спліту herdr
```

Ключ задачі читається з імені гілки, тому `feature/ACME-42-thing` дає `ACME-42`.
Передайте ключ явно, щоб працювати з іншою задачею звідки завгодно.

### Панель

`wipline-tui` працює в будь-якому терміналі. `wipline-pane` — тонкий лончер для
[herdr](https://github.com/persiyanov/herdr): він відкриває вузьку колонку поруч із
панеллю, у якій ви зараз, і визначає задачу з каталогу тієї панелі, а якщо не вийшло —
з назви її таба. Тобто панель відкривається на тій задачі, над якою ви справді
працюєте, а дошку-вибірку показує лише тоді, коли визначити не змогла.

Прив'яжіть до клавіші (`config.toml` у herdr):

```toml
[[keys.command]]
key = "f2"
type = "shell"
command = "wipline-pane toggle"
description = "phase board"
```

По одному екземпляру на таб, тому кілька задач можуть мати власні панелі відкритими
одночасно.

## Конфіг

`.wipline.json` у вашому репозиторії, шукається вгору від робочого каталогу.
Користувацький `~/.config/wipline/config.json` задає типові значення; файл проєкту
перемагає.

```json
{
  "taskPattern": "[A-Z][A-Z0-9]*-\\d+",
  "stateDir": "~/.local/state/wipline",
  "phases": [
    { "name": "spec",    "stage": "planning" },
    { "name": "build",   "stage": "build" },
    { "name": "checks",  "stage": "build" },
    { "name": "review",  "stage": "review" },
    { "name": "ship",    "stage": "handover" }
  ]
}
```

- **`taskPattern`** — регулярний вираз, що описує ваші ключі задач. Типово у стилі
  Jira; для issue в GitHub візьміть `#\\d+`.
- **`stateDir`** — де живуть журнали. Свідомо поза репозиторієм: це ваш стан, а не
  стан проєкту, і йому не варто перетворюватись на конфлікти злиття.
- **`phases`** — процес, по порядку. Порядок важливий: `reset` каскадить за ним, а
  `next` — це перша фаза, яка ще не пройдена.
- **`stage`** — підпис для групування списку. **Фази з однаковою стадією мають бути
  сусідніми**: панель починає нову групу щоразу, коли стадія змінюється, тому стадія,
  що трапилась двічі, намалюється двічі. Завантаження конфігу відхиляє такий випадок,
  а не малює щось незрозуміле.

## Підключення автоматизації

**Ось частина, яка має значення.** Чеклист, який відмічають руками, псується саме
тоді, коли ви зайняті — тобто коли він був потрібен. Кожна фаза, що лишає слід, має
відмічати себе сама, і тоді панель — це вітрина, а не рутина.

Контракт — один рядок: **усе, що вміє запустити команду, вміє записати фазу.**

```bash
wipline done <phase> --by <who> [--detail "k=v"]
```

Операція ідемпотентна — ідентичний повтор не дописує нічого — тому її можна викликати
щедро з вотчера чи хука, не засмічуючи `history`.

### Одне правило, якого слід дотриматись

**Крок, що не пройшов власну перевірку, не має записувати свою фазу.** Незаписана
фаза — невелика незручність; фаза, яка бреше про успіх, гірша за повну відсутність
відстеження. Тому прив'язуйте кожен виклик до того, що робота справді відпрацювала:

```bash
npm run lint && wipline done lint --by ci
```

### Claude Code

Два механізми, і вибір залежить від того, чи володієте ви тим, що виконує роботу.

**1. Скіли й команди, якими ви володієте — один рядок у кінці.**

У кінці процедури скіла, після того як його власна перевірка пройшла:

````markdown
Запишіть фазу:

```bash
wipline done tests-review --by reviewing-tests
```

Тільки на зеленому шляху — червоний гейт означає, що рев'ю не завершилось. Код
виходу 3 означає, що гілка не несе ключа задачі: проігноруйте й не згадуйте у звіті.
````

**2. Скіли, якими ви НЕ володієте — хук на артефакт.**

Вбудовані скіли та скіли з кешу плагінів, які оновлення перезапише, редагувати не
можна. Замість цього хукайте *артефакт*: файл, який вони пишуть, або інструмент, який
вони викликають. У `.claude/settings.json`:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit|MultiEdit",
        "hooks": [{ "type": "command", "command": "sh .claude/hooks/wipline-phase.sh", "timeout": 10 }]
      }
    ]
  }
}
```

І сам хук, який **мусить падати відкрито** — він запускається в кожній сесії, у тому
числі в тих, що не мають до задачі жодного стосунку:

```sh
#!/bin/sh
set -u
input=$(cat)
command -v jq >/dev/null 2>&1 || exit 0
command -v wipline >/dev/null 2>&1 || exit 0

repo=$(printf '%s' "$input" | jq -r '.cwd // empty')
[ -n "$repo" ] || exit 0
cd "$repo" 2>/dev/null || exit 0

file=$(printf '%s' "$input" | jq -r '.tool_input.file_path // empty')
case "$file" in
  */specs/*) phase=spec ;;
  */plans/*) phase=plan ;;
  *) exit 0 ;;
esac

wipline done "$phase" --by hook --detail "path=$file" >/dev/null 2>&1
exit 0
```

Дві речі, які тут легко зробити неправильно, обидві вивчені на власних помилках:

- **Спершу `cd` у `cwd` сесії.** wipline читає ключ задачі з поточної гілки, а хук не
  обов'язково стартує в тому каталозі, де працює сесія — особливо з git worktree, де
  спільний каталог конфігу може бути симлінком у зовсім інший checkout. Помилитесь тут
  — і фази записуватимуться в іншу задачу.
- **`exit 0` на кожному шляху.** Хук, що падає, ламає непричетну роботу, а це набагато
  гірше за пропущену відмітку.

**3. Виклик інструмента як сигнал.** Коли скіл звітує через інструмент, хукайте ім'я
цього інструмента, а не шлях до файла, і читайте payload, щоб вибрати між `done` та
`open`. Для інструмента рев'ю, який повертає знахідки:

```sh
total=$(printf '%s' "$input" | jq -r '(.tool_input.findings // []) | length')
if [ "$total" -eq 0 ]; then
  wipline done review --by review-tool >/dev/null 2>&1
else
  wipline open review --by review-tool --detail "n=$total" >/dev/null 2>&1
fi
```

Ось для чого існує `open`: крок відпрацював, і дещо лишилось зробити.

### git, CI і вотчери

У wipline немає нічого специфічного для Claude. Будь-що, що вже знає про завершення
кроку, може про це сказати.

**Зелений прогін тестів, проштампований комітом, на якому він був зелений:**

```bash
npm test && wipline done checks --by ci --detail "head=$(git rev-parse --short HEAD)"
```

Штамп `head=` дає річ, яку варто зрозуміти: **фаза, записана з head, повідомляється
як `open reason=stale`, щойно гілка пішла далі.** «Тести пройшли» — це факт про коміт,
а не про гілку, тому після наступного коміту фаза сама перестає бути пройденою й знову
з'являється як ваш `next`. Працює для будь-якої фази, не тільки для тестів —
штампуйте все, чия правдивість спливає разом зі зміною коду.

**Створений merge request:**

```bash
iid=$(gh pr view --json number --jq .number) && wipline done mr --by gh --detail "iid=$iid"
```

**Post-commit хук, що відмічає розробку в процесі:**

```sh
# .git/hooks/post-commit
wipline wip dev --by git >/dev/null 2>&1 || true
```

### Що автоматизувати не вийде

Деякі кроки не лишають слідів: ви протестували руками, ви самі прочитали дифф. Такі
залишаються ручними — і саме для цього існує `wip`: відмітьте, над чим ви, а знімати
позначку не треба нікому. Будь-який пізніший запис по тій самій фазі її замінює, тому
та автоматизація, що врешті завершить крок, зніме її сама.

## Журнал

Один файл на задачу в `stateDir`, поля розділені табуляцією, тільки дописування:

```
2026-08-19T09:14:02Z	start	done	starting-a-task
2026-08-19T10:02:41Z	spec	done	hook	path=docs/spec.md
2026-08-19T13:20:10Z	checks	done	ci	head=c7a57c0 ran=lint,types
2026-08-19T14:05:33Z	review	open	review-tool	n=3
2026-08-20T09:00:00Z	dev	reset	me	reason=qa-feedback
```

П'ять полів: час, фаза, стан, хто і вільний `k=v` деталь. Дописування короткого рядка
атомарне, тому кілька сесій і хуків можуть писати одночасно без блокування й без
втрати записів — саме тому це лог, а не JSON-документ.

Читання — зворотна операція: згорнути записи, по кожній фазі перемагає останній,
`reset` очищає свою фазу й усе після неї. Усе це живе в одному покритому тестами
модулі, тому всі поверхні узгоджені між собою.

## Розробка

```bash
node --test test/*.test.mjs
```

Без залежностей і без збірки. `lib/phases.mjs` — чистий: словник і згортка, жодного
введення-виведення. `lib/store.mjs` володіє файлами. `lib/view.mjs` — чиста
відмальовка, тому розкладка тестується без терміналу.
